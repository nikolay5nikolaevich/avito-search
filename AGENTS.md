# AGENTS.md

Общая инструкция для ИИ-агентов в этом репозитории. Codex читает её напрямую,
Claude Code — через импорт в `CLAUDE.md`. Прямые указания пользователя в чате
важнее этого файла и любых скиллов.

## Проект
Локальный сервис для продавца на Авито. Главный сценарий — автовыкладка:
пользователь заполняет форму, сервис готовит N уникальных вариантов (текст + фото)
и публикует их на Авито через живой Chrome по CDP. Рядом — аналитика спроса по
городам, разбор продавца, рассылка в чат Авито, поиск под перепродажу.

Пользователь — новичок (JS, немного Python, Node не знает), общение по-русски.
Ему отдаём готовые команды и файлы целиком, а не диффы.

## Публикация тратит деньги
Публикация реальная, платная и необратимая. Путь в `publisher.py`: форма →
«Продолжить» → экран стоимости просмотра (slider) → «Продолжить с минимальной
ценой» → `/pro/performance` → «Продолжить без услуг». Этот участок работает
по принципу fail-closed: при любой неопределённости — остановка с понятной
причиной, решение принимает человек.

- Подпись кнопки, услугу и цену сверяем с известным списком (`_norm_label`).
  Незнакомое значение — остановка: догадка здесь стоит денег.
- Ретраим только безопасные GET. Денежный клик выполняется ровно один раз —
  повтор может оплатить услугу дважды.
- Цену ставим штатным slider и подтверждаем обратным чтением (`Decimal`). Нужного
  значения нет на шкале — остановка с показом соседних значений.
- Отказ от услуг — один клик и только на `/pro/performance`.
- Пакет публикации один за раз: межпроцессный lock `tmp/publish/publish.lock`,
  второй `/start`/`/resume` получает 409. Прерванный пакет продолжают с checkpoint
  (`POST /api/publish/resume/{job_id}`, `publish_state.py`, `resume_plan`) или
  закрывают явно (`POST /api/publish/close/{job_id}`). Повторный запуск пакета
  с формы создаёт платные дубли; перезапуск сервера безопасен — состояние на диске.
- Об успехе судим по `step`/`resume_plan`: `items_published: 0` не исключает,
  что денежный клик уже прошёл.
- Статус «Отправлено» означает прохождение экрана услуг. Модерацию не отслеживаем —
  так решил пользователь.

Лучший источник по реальному поведению Авито — разбор боевого прогона 17/17:
`docs/reports/2026-08-16-publication-errors.md`.

## Запуск
Авито банит браузеры, запущенные Playwright, поэтому сервис подключается к
настоящему Chrome пользователя:
1. `start-chrome.bat` — Chrome с портом 9222; пользователь сам входит на avito.ru.
2. `python backend/app.py` — сервер на `localhost:7777`.

Интерфейс собирается один раз: `cd frontend && npm install && npm run build`.
Env: `AVITO_CDP_URL` (для IPv4 — `http://127.0.0.1:9222`), `AVITO_MAX_ITEMS`.

## Где что лежит
- `backend/publisher.py` — весь живой сценарий публикации.
- `backend/preparation.py` + `text_variation.py` / `photo_variation.py` — подготовка
  вариантов. Уникализация детерминированная: дословное описание + уникальный
  артикул, фото — лёгкий зум.
- `backend/category_profiles.py` — поля и размерные сетки категорий.
- Селекторы разделены: `avito_publish_selectors.py` — форма публикации,
  `avito_selectors.py` — страница выдачи.
- `backend/browser.py` — подключение по CDP; `backend/diag.py` — разведка живой
  страницы в `debug/`.
- `docs/reports/` — разборы прогонов и аудиты, `docs/specs/` — спеки,
  `docs/README.md` — индекс документации (обновлять при добавлении документа).
- `docs/_internal/` (не в git) — планы, дизайны, брифы, отчёты о задачах.

## Грабли
- Сервер без auto-reload: после правок бэкенда его перезапускают. Симптом забытого
  перезапуска — фронт шлёт новый контракт, бэк отвечает по старому.
- Playwright закреплён на 1.60.0: на 1.62 publish-smoke падал по EPIPE. Тот же EPIPE
  встречался и на 1.60.0 — перед обновлением перепроверить.
- CDP виснет на «ws connected → Timeout» из-за зависших вкладок Авито. Лечение —
  оставить одну вкладку avito.ru.
- Автокомплиты (бренд, адрес) принимают значение только кликом по пункту подсказки.
  Адрес ищем внутри контейнера гео, иначе выбирается чужой город.
- Профиль продавца — бесконечная лента с повторами: дедуп по ID. Витрина
  `/brands/<id>/all` сначала раскрывается кнопкой «Показать все».
- Изменил метрики аналитики — удали `cache.db`: ключ кэша от этого не меняется.
- В `debug/` персональные данные — содержимое оттуда наружу не выносим.
- Авито открывается только с РУ-IP, Claude — только без него. Живые проверки
  разведены по времени: пользователь запускает `diag.py`, агент разбирает `debug/`.

## Как работаем
**Роли.** Оркестратор — сессия, которая говорит с пользователем: декомпозирует,
пишет брифы, принимает результат. Субагенты исполняют брифы. Субагент стартует
без истории чата, поэтому бриф содержит весь нужный контекст. Независимые задачи
идут параллельно, зависимые — по очереди; мелочь быстрее сделать самому.

**Pipeline фичи.** spec → design → plan → brief → execution → report → acceptance.
Крупное режем на части с отдельной приёмкой.

**Бриф.** Зачем / Контекст / Решения, которых нет в спеке / Границы / Можно без
спроса / Готово, когда. Контекст — основная часть: точки входа, что уже есть,
почему так решено. На спеку ссылаемся, не пересказываем. 3–4 границы, у каждой
причина. Цель описываем исходом, путь оставляем исполнителю. В аудите просим всё
найденное — ранжирует оркестратор.

**Feasibility gate.** Неизвестно, сработает ли подход (источник данных, поведение
Авито) — сначала дешёвая проверка с заранее заданным порогом. Порог не взят —
отчёт `BLOCKED` с доказательствами и альтернативой.

**Acceptance-тесты.** Тесты-доказательства пишет агент, который не писал проверяемый
код, — заранее, от ожидаемого итога: спека, денежные правила, слова пользователя.
Тест сначала red, после правки green; ожидания после прогона не ослабляем.

**Факты вместо догадок.** Поведение Авито узнаём по снимкам живых страниц и логам.
Каждый боевой прогон — разбор в `docs/reports/`, каждый новый сбой — строка в
`docs/reports/publish-error-registry.md` (симптом → причина → лечение). Перед
изменением денежного участка — аудит, где каждую находку пытаются опровергнуть.

**Готово, когда** код проверен тестами затронутого участка и есть отчёт: какие
файлы изменены, какие проверки прогнаны с точным результатом («publish-smoke:
34 passed»), что не вышло и почему.

**Договорённости с пользователем.**
- Удаление и перенос в `trash/` — после его явного «да» на показанный список.
  `trash/` — карантин, чистит его он сам.
- Команды в его среде (Docker, установки, живой Авито) он запускает сам — даём
  готовые команды построчно.
- `.env` с ключами Авито читает только `backend/env_file.py`.
- Коммиты — по его просьбе, сообщения нейтральные, без упоминаний ИИ.

## Стиль кода
PEP 8, type hints, комментарии и логи по-русски, `logging` вместо `print`.
Сбой одного объявления, города или шага — лог и пропуск со статусом; пакет
продолжает работу.
