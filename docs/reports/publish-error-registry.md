# Реестр ошибок публикации

Живой рабочий документ: сюда складываем каждый наблюдённый сбой публикации,
его причину и способ устранения. Источник данных — `logs/publisher.log`
(все прогоны) и дампы в `debug/publish/<job_id>/`.

Обновлён: 25.10.2026. Последний разобранный сбой — E-20:
фото загружены, старые селекторы не распознали превью.

Смежные документы:
- `docs/reports/2026-08-16-publication-errors.md` — разбор боевого прогона 17/17,
  лучший источник по реальному поведению Авито.

## Как читать

Каждая ошибка: **симптом** (что видно в UI/логе) → **причина** → **что делать**.
Приоритет: P1 стоит денег или блокирует пакет, P2 портит результат, P3 шум.

## P1. Сеть и подключение

### E-01. `net::ERR_ABORTED` / `ERR_NAME_NOT_RESOLVED` на `open_form`

**Симптом.** В UI: «Непредвиденная ошибка на шаге open_form: Page.goto:
net::ERR_ABORTED at https://www.avito.ru/additem». Отправлено 0 из N.
Дамп пустой — только `error.txt`, без скриншота и HTML.

**Не путать.** Выглядит как «Авито долго грузит форму», но это НЕ таймаут
и не медленный сайт. `ERR_ABORTED` = соединение оборвано посреди навигации.

**Причина — на 16.08.2026 не установлена.** Рабочие версии ниже.

> **ВАЖНО: как НЕ надо диагностировать.**
> `curl` из окружения ассистента **не является** индикатором доступности Авито
> для Chrome пользователя — они ходят через разные сетевые каналы (у ассистента
> не-РУ выход, у Chrome РУ). Живой Авито отдаёт на голый `curl` **HTTP 403**
> (антибот, без браузерных заголовков), а `HTTP 000`/таймаут означает лишь,
> что не прошёл сам curl. Ни то, ни другое не говорит о состоянии Авито
> в браузере. Единственный достоверный признак — вкладки Авито в Chrome
> открываются руками.
>
> Ошибка допущена 16.08.2026: из `HTTP 000` был сделан неверный вывод
> «Авито недоступен, VPN переключился». Перепроверка дала `HTTP 403` за 0.7 с
> при полностью рабочем Авито в браузере.

**Версия A (отвергнута): пропал РУ-IP.** Не подтвердилась — Авито в Chrome
пользователя работал исправно, рекламные фреймы показывают РУ-IP
`66.90.91.195` (Москва, Билайн).

**Версия B (отвергнута): навигация в чужую занятую вкладку `/additem`.**
Не подтвердилась: `run_publish_job` открывает **свою** вкладку
`context.new_page()` (`publisher.py:2601`) и вкладки пользователя не трогает.
Конфликта нет.

**Версия C (основная): временный сетевой сбой на стороне канала Chrome.**
Ключ — тайминг в логе:
```
13:55:49  Шаг 2/16: open_form          ← старт goto
13:56:12  WARNING  DNS ... недоступен   ← 23 с ждали, ERR_NAME_NOT_RESOLVED
13:56:18  ERROR    net::ERR_ABORTED     ← вторая попытка, ~4 с
```
Первый `goto` висел 23 с и упал по DNS — резолвер не ответил. Это реальный
сбой в канале Chrome (VPN-клиент моргнул, DNS-таймаут, перезапуск туннеля),
кратковременный: к моменту разбора Авито работал штатно. `ERR_ABORTED` на
второй попытке — следствие того же обрыва, соединение оборвано на лету.

Важно: сбой был **временным и уже прошёл**. Отдельных действий не требует,
кроме устойчивого ретрая (см. ниже).

**Версия D: антибот Авито** оборвал навигацию. Менее вероятна — при антиботе
обычно приходит капча/иной экран, а не DNS-таймаут на 23 с.

**Что делать.** Просто перезапустить пакет (при `items_published: 0` —
целиком, см. E-05). Если `ERR_ABORTED`/DNS повторится на том же месте —
причина устойчивая, тогда смотреть VPN-клиент и его DNS.

**Дефект кода.** `_goto_additem_with_dns_retry` (`backend/publisher.py:1028`)
ретраит **только** `ERR_NAME_NOT_RESOLVED`:
```python
is_dns_failure = "net::ERR_NAME_NOT_RESOLVED" in str(exc)
```
`ERR_ABORTED`, `ERR_CONNECTION_RESET`, `ERR_INTERNET_DISCONNECTED`,
`ERR_CONNECTION_TIMED_OUT`, `ERR_TIMED_OUT` падают сразу, хотя это тот же
класс временных сетевых сбоев. Задержки `(2.0, 5.0)` с — слишком коротко
для переключения VPN (нужны десятки секунд).

**Починка (предложение).**
1. Расширить список ретраибельных ошибок до всех перечисленных выше.
2. Увеличить задержки до `(5.0, 15.0, 30.0)`.
3. **Перед стартом пакета** — предполётная проверка достижимости `avito.ru`:
   один GET, и при неуспехе внятное «нет РУ-IP» вместо падения на первом же
   объявлении. Дёшево и снимает весь класс.

### E-02. `connect_chrome`: WebSocket подключён, но Timeout

**Симптом.** `Задача …, шаг connect_chrome: failed — WebSocket подключён, но …`.
В логах — 28 срабатываний (`cdp-timeout-test`).

**Причина.** Лишние CDP-цели: висящие вкладки Авито, рекламные iframe
(adriver), blob-цели, воркеры. `connect_over_cdp` перебирает их все и виснет.
Не связано ни с профилем, ни с версией Chrome.

**Как подтвердить — считать ТОЛЬКО цели типа `page`.**
```bash
curl -s http://127.0.0.1:9222/json/list \
  | python -c "import json,sys; t=json.load(sys.stdin); [print(x['type'],x['url'][:80]) for x in t]"
```
> **Не использовать** `grep -c '"type"'` — он считает и `iframe`, и `worker`,
> которые являются содержимым обычных вкладок, а не отдельными окнами.
> 16.08.2026 такой подсчёт дал «11 вкладок» при реальных **трёх**, и отсюда
> вырос ложный вывод «пользователь не закрыл вкладки». Вкладки = только `page`.

Норма — 1–3 цели `page`. Проблема — заметно больше, либо дубли `/additem`.

**Случай 16.08.2026.** 11 целей всего, но по типам: **3 `page`**
(`localhost:8000`, `avito.ru/additem`, `/profile/pro/items`),
4 `iframe` (реклама adriver внутри страниц Авито), 4 `worker` (воркеры Авито).
Это нормальное состояние трёх открытых вкладок, а не замусоренный браузер.

**Что делать.** Ориентироваться на число `page`. Значимо здесь одно:
открытая `/additem` конфликтует с `page.goto()` на неё же (см. E-01 версия B)
и провоцирует E-06.

**Починка (предложение).** Перед `connect_over_cdp` отфильтровать цели:
брать только `type == "page"` с хостом `avito.ru`, игнорируя `blob:`,
`iframe` и рекламные домены. Плюс диагностическое сообщение
«вижу N целей, ожидаю 1» вместо немого таймаута.

### E-04. `connect_chrome`: Chrome не найден по адресу

**Подтверждённый случай 25.10.2026.** Задача
`6ae8ac54-66a6-4c91-b3c6-fe05b9108954`: `WinError 10061`, 0/5,
`step=connect_chrome`. Процессов Chrome нет, `127.0.0.1:9222/json/version`
отвергает соединение. Причина — браузер для Авито закрыт, а не ошибка фото
или геолокации. Запущен существующий `start-chrome.bat`, CDP подтвердил Chrome
155 и WebSocket, Авито открыт в сохранённом профиле. Штатный resume использован
для той же задачи с №1; новый пакет не создавался. Обычный Chrome без параметра
`--remote-debugging-port=9222` не заменяет это окно.
Итог после восстановления: 26.10.2026 отправлено 5/5, ошибок и пропусков нет,
ставка каждого — 0,80 ₽ за просмотр. Отчёт:
[2026-10-26-iphone17-cdp-recovery.md](2026-10-26-iphone17-cdp-recovery.md).

**Симптом.** `failed — Chrome не найден по адресу…`.

**Причина.** Chrome не запущен через `start-chrome.bat`, либо IPv6/IPv4:
`localhost` резолвится в `::1`, а Chrome слушает `127.0.0.1`.
Либо Chrome 149+ без флага `--remote-allow-origins=*`.

**Что делать.** `start-chrome.bat`; `AVITO_CDP_URL=http://127.0.0.1:9222`
(явный IPv4); проверить наличие `--remote-allow-origins=*` в bat-файле.

## P1. Деньги и дубли

### E-05. Остановка посреди пакета → riск двойной оплаты при РУЧНОМ перезапуске

**Симптом.** Пакет упал на объявлении K из N. Часть объявлений уже отправлена
и, возможно, оплачена.

**Причина.** Штатное возобновление (checkpoint + кнопка «Продолжить» +
`POST /api/publish/resume/{job_id}`) есть и безопасно пропускает уже
созданное — риск двойной оплаты появляется, только если проигнорировать эту
кнопку и запустить публикацию заново вручную с формы (новый `job_id`
начинает счёт объявлений с №1).

**Что делать.** Открыть экран публикации (или `GET /api/publish/status/<job_id>`)
и нажать «Продолжить» — сервис сам решит, повторить текущее объявление
(`retry_item`, если денежного клика ещё не было) или пропустить его и
продолжить со следующего (`skip_item`, если оно уже могло быть создано).
`items_published: 0` **не значит** «на Авито ничего нет»: денежный клик мог
уже пройти на текущем объявлении — проверяйте `step`/`resume_plan`, а не
только счётчик. Если продолжать пакет не нужно — закрыть задачу кнопкой
«Закрыть задачу» (`POST /api/publish/close/{job_id}`), а не запускать новую
публикацию поверх старой.

**Случай 16.08.2026.** `items_published: 0`, `published_urls: []` — на тот
момент штатного resume ещё не было, перезапуск целиком был единственным
вариантом и прошёл без дублей.

### E-06. Авито переоткрыл уже обработанную форму

**Симптом.** `Объявление K/N: поле названия уже содержит наше название …` →
`UserActionRequired`, сценарий останавливается.

**Причина.** Защита от дубля (`publisher.py:1007`). Авито вернул форму
с уже заполненными данными вместо чистой. Часто — следствие висящей
вкладки `/additem` из E-02.

**Что делать.** Это **правильное** поведение, не баг: остановка дешевле дубля.
Закрыть лишние вкладки, проверить `items_published`, перезапустить остаток.

### E-07. `open_next_form`: Авито вернул неожиданный экран

**Симптом.** `шаг open_next_form: failed — Авито вернул н…`, 20 срабатываний
(`partial-publication-test`).

**Причина.** После отправки объявления Авито ведёт не на чистую `/additem`,
а на промежуточный экран (услуги, промо, опрос).

**Что делать.** Проверить `items_published`, дальше как E-05.

## P2. Форма и поля

### E-08. Превью фото не дождались: «за 120 с появилось K/N»

**Актуально на 25.10.2026.** Описанное ниже продолжение с неполным набором —
историческое поведение. Сейчас недобор превью вызывает `StepError` и
останавливает пакет до публикации. Нельзя считать причиной только медленную
загрузку: сначала проверить скриншот, DOM и сеть (см. E-20). Не повышать таймаут
и не отправлять фото повторно, если они уже загружены.

**Симптом.** `За 120 с появилось 7/8 превью — продолжаю с тем, что есть`.
Наблюдалось 7/8 и 4/5.

**Причина.** Загрузка фото на Авито медленнее таймаута. Сценарий продолжает
осознанно — но объявление уходит **с неполным набором фото**.

**Что делать.** Проверять опубликованные объявления глазами: часть фото
может отсутствовать.

**Починка (предложение).** Поднять таймаут; при недоборе — повторно отдать
недостающие файлы, а не молча продолжать. Сейчас это тихая потеря качества.

### E-09. `SELECTOR_MISS` на превью фото

**Обновление 25.10.2026.** На актуальной форме ни один прежний CSS-кандидат
не находит фото. Добавлен подтверждённый маркер `preview(<id>)/image` внутри
`images`; разбор и регрессионные проверки — E-20. Ниже исторический случай.

**Симптом.** Три подряд `SELECTOR_MISS` (`[data-marker='image']`,
`[data-marker='thumbnail']`, `[class*='photo-list'] img`), затем успех на
`[class*='uploader'] img`. Каждый промах — 5 с ожидания.

**Причина.** Список кандидатов в неверном порядке: рабочий селектор — последний.
Стабильно теряется ~15 с на каждом объявлении (на 17 объявлений — 4+ минуты).

**Что делать.** Не блокирует, работает.

**Починка (предложение).** Переставить `[class*='uploader'] img` первым.
Правка на одну строку, экономит минуты на пакет.

## P3. Диагностика

### E-15. Скриншот/HTML шага не сохранены

**Симптом.** `Скриншот шага X не снят: Target page, context or browser has
been closed`. Массово (7 на `open_form`, 4 на `fill_view_price`, …).

**Причина.** Дамп снимается после того, как страница уже мертва. При сетевых
обрывах (E-01) это всегда так — остаётся `error.txt` без визуала.

**Что делать.** Опираться на `logs/publisher.log`: там полная картина.

**Починка (предложение).** Снимать скриншот **до** закрытия вкладки, либо
при живой странице по ходу шага. Сейчас дамп бесполезен ровно в тех случаях,
когда нужнее всего.

### E-16. `save_draft`: таймаут 0.0 с

**Симптом.** `save_draft: таймаут 0.0 с, вкладки контекста: [...]`,
32 срабатывания — самое частое предупреждение в логах.

**Причина.** «0.0 с» — вырожденное значение, таймаут посчитан неверно.
Похоже на дефект расчёта, а не на реальный таймаут.

**Починка (предложение).** Разобрать вычисление таймаута в `save_draft`.
Сообщение в текущем виде вводит в заблуждение.

### E-17. iPhone: найденное радио состояния скрыто

**Симптом.** Предполётная проверка останавливается на `connect_chrome`:
`params[121588]/2850684` найден, но `element is not visible`.

**Причина.** Подробное состояние присутствует в скрытом шаге формы.
Краткое состояние `params[110395]` находится в видимом шаге, но движок
безусловно начинает с подробного.

**Лечение.** Исправлено заполнение видимого состояния с обратной
проверкой; скрытое подробное поле не кликается принудительно. После
перезапуска backend продолжать
существующий пакет через штатный resume, учитывая денежный маркер.
Разбор: `2026-10-20-iphone-publication-errors.md`.

### E-18. iPhone: пропущены SIM, история и упаковка

**Симптом.** После «Продолжить» остаётся `/additem`, три ошибки
«Укажите значение параметра»; сервис сообщает, что экран стоимости
просмотра не подтверждён.

**Причина.** Профиль телефона не заполнял обязательные поля `184666`,
`184667`, `167055`.

**Лечение.** Добавлено заполнение SIM + eSIM, неактивированного состояния
и запечатанной упаковки только при явном подтверждении в описании;
неизвестные и противоречивые данные останавливают сценарий. После клика
не сбрасывать `money_click`: проверить кабинет и существующий черновик.
Первый черновик восстанавливается отдельно, остальные — штатным resume.
Разбор: `2026-10-20-iphone-publication-errors.md`.

### E-19. /additem: шапка загрузилась, форма отсутствует

**Симптом.** `open_form` за 30 с не находит крошки категории или мастер;
в дампе только шапка и пустая основная область, без видимой капчи.

**Причина.** Форма приложения Авито не отрисовалась. Первопричина загрузки
по одному HTML не установлена; считать это капчей без доказательств нельзя.

**Лечение.** Проверить checkpoint и денежный маркер. При `money_click: null`
на `open_form` штатный resume повторяет только текущее объявление.
Не начинать новый пакет и не повторять финансовые клики.
Случай 20.10.2026: после четырёх отправленных возобновлён №5.

### E-20. iPhone: все фото загружены, но ожидание завершается с `0/6`

**Симптом.** 25.10.2026, задача `20385858-5ba2-4dd3-ac2f-3d42e0d8d85a`:
`upload_photos`, 120 секунд ожидания, `0/6 превью`, пакет остановлен на первом
объявлении из пяти. На сохранённом скриншоте при этом есть все шесть фото.

**Доказанная причина.** В диагностике шесть upload-ответов HTTP 200.
В сохранённом DOM фото имеют `data-marker="preview(<id>)/image"` внутри
`data-marker="images"`. Старые кандидаты опирались на CSS-классы или другие
маркеры: все пять дали 0 на том же DOM. Это ошибка распознавания превью,
а не доказательство сбоя сети, повреждения файлов или антидубля Авито.

**Исправление.** В `avito_publish_selectors.py` первым добавлен
`[data-marker='images'] img[data-marker^='preview('][data-marker$=')/image']`.
На реальном HTML он возвращает ровно 6. Динамические ID не фиксируются,
вложенные контейнеры не удваивают счётчик. Посторонние картинки не учитываются.
Ожидание полного набора, таймаут и остановка при недоборе сохранены.

**Продолжение.** После перезапуска сервера использовать штатное возобновление
этой задачи. Проверенный checkpoint: `failed`, `step=upload_photos`,
`items_published=0`, `item_index=1`, `money_click=null`;
`resume_plan` возвращает `retry_item`, `start_index=1`, `items_total=5`.
Разбор не запускал resume или новую публикацию.

**Проверки.** `test_photo_preview_dom.py`: 5 passed; старый
`test_photo_preview_wait.py`: 1 passed. Новый тест сначала воспроизвёл сбой,
после исправления прошёл с прежними ожиданиями. Разбор:
[2026-10-25-photo-preview-selector.md](2026-10-25-photo-preview-selector.md).

### E-21. Гео-подсказка перерисовалась перед кликом, `nth(4)` исчез

**Симптом.** Задача `3cff2490-adfc-407e-8017-8683b8cc40dd`, 25.10.2026:
первое объявление из пяти остановлено на `fill_address` с таймаутом клика
`custom-option(...).nth(4)`. В конечном DOM подходящий адрес уже единственный,
с индексом 0. Фото при этом загрузились успешно (6/6).

**Причина.** Авито обновил список после чтения вариантов. Локатор по позиции
из старого списка исчезает либо указывает на другой адрес. Таймаут клика
также выходил за пределы повторного выбора.

**Решение.** Один снимок видимых текстов через `evaluate_all`; локатор клика
фильтруется по точному выбранному тексту, без сохранения индекса. Таймаут
клика ограничен общим сроком выбора; при обновлении списка повторяется чтение.
После клика проверяются hidden `address` и `locationId`.

**Окончательное уточнение пользователя.** Подходят Москва или Московская
область. При совпадении улицы/дома разрешён переход Москва ↔ область.
Это не разрешение выбирать другую улицу/дом или другой регион.

**Проверки.** 7 новых DOM-тестов и 7 прежних тестов autocomplete проходят.
В окончательной версии область допускается, точная Москва имеет приоритет,
другая улица и другой дом не принимаются.
Регрессии: `tests/test_address_suggest_rerender.py`. По прямой просьбе
пользователя пакет возобновлён через штатный resume с первого объявления;
окончательный результат фиксируется в отчёте прогона.

### E-22. После адреса финальная кнопка временно имеет другую подпись

**Симптом.** После отправки первого объявления задача `3cff2490-adfc-407e-8017-8683b8cc40dd`
остановилась на `continue_listing` второго: прочитано `Разместить timing`.
В сохранённом после остановки DOM уже находится `Продолжить timing`.

**Подтверждено.** Между проверкой и дампом подпись изменилась; причина
перерисовки предположительно связана с обновлением формы после адреса.
Наличие тарифа с оплатой просмотров само по себе не доказывает допустимость
неизвестной кнопки «Разместить».

**Решение после независимого аудита.** До финансовой границы до пяти секунд
ждать точную известную подпись и доступность кнопки. Если неизвестное название
сохраняется — остановка без клика. Allowlist не расширен. Один клик,
денежный маркер, checkpoint и проверка `/cpxpromo` оставлены прежними.

**Проверки.** 4 новых теста `test_regional_continue_button.py` (сначала red,
после исправления green), 11 прежних проверок перехода и денежного маркера
прошли. Проверены временная подпись, временная недоступность, постоянная
неизвестная подпись без клика и неизменность allowlist.

### E-23. На цене просмотра индекс кнопки стал указывать на стрелку

**Симптом.** При завершении уже созданного объявления №2 (8420722316)
разрешённая кнопка была найдена как `button.nth(1)`, но перед кликом список
изменился и локатор разрешился в стрелку «←» (`action-buttons-secondary`).
Playwright остановился на проверке положения: `outside of the viewport`.

**Решение и аудит.** Возвращать из `_find_view_price_action` локатор,

Не сохранять позицию кнопки. Неизвестный суффикс и неоднозначность не разрешают
подтверждение. В конкретном случае цену подтвердил пользователь; повторного
клика цены автоматизацией не было. Экран услуг пройден штатной проверкой,
после подтверждённого кабинета сохранён успех №2.

**Проверки.** `test_view_price_action_rerender.py`: 3 passed, сначала red;
проверки цены из `test_publish_financial_flow.py` проходят.

### E-24. Город Московской области сравнивался с названием всего региона

**Решение.** Не отключать проверку города. До выхода с формы сохранять

### E-25. iPhone 17 распознан, но фото прямо в папке памяти не видны

**Симптом.** Фото в `library/iphone/Iphone 17/256 GB/*.jpg`, модель распознана,
общий текст найден, но список паков пуст. Общая ошибка порядка фото скрывает
точную причину каталога.

**Причина.** Старый каталог читает только подпапки фотопаков в папке памяти.

**Решение.** Фото прямо в папке памяти доступны как неявный пак «Основной»
с внутренним ID `__memory__`. Совместно работают именованные паки. Папки моделей
сопоставляются без учёта регистра и повторных пробелов. Файлы не переносятся.
При смене модели сбрасываются старый preview/order; ключ модели/памяти
защищает от переноса старого случайного пака из сохранённой формы.
Конкретная ошибка каталога больше не затирается общей ошибкой превью.

**Проверки.** 7 новых тестов прямого пака; полный набор iPhone: 66 passed.
На пользовательских четырёх JPEG новый сервер вернул доступный пак с четырьмя
фото. Подробности: `2026-10-25-iphone-direct-memory-pack.md`.

## Лишние пустые строки в черновиках (21.10.2026)

**Симптом.** В подготовленных описаниях появляются лишние пустые строки,
включая строки перед телефоном. Воспроизведено локально, без публикации.

**Причина.** На Windows `Path.write_text` повторно переводил CRLF в CRCRLF;
`read_text` читал результат как два переноса. Повреждались также исходники
для последующей перегенерации.

**Лечение.** Во всех четырёх записях описания в `preparation.py` указан
`newline=""`. После перезапуска сервера заново вставить исходный текст
в форму подготовки или вручную исправить существующий черновик. Перегенерация
из уже повреждённого исходника не убирает накопленные пустые строки.
Проверки: 6 новых regression-тестов, 6 тестов вариантов текста и 13 самотестов
подготовки прошли. Подробности: `2026-10-21-draft-description-newlines.md`.
