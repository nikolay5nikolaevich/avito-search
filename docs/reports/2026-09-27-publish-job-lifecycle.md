# Один пакет публикации за раз — 27.09.2026

## Что изменилось

`/start` и `/resume` допускают только один активный пакет. Новая задача сразу получает
`queued` в памяти до чтения фото, поэтому второй запрос в том же event loop видит
резервирование. Перед запуском фоновой задачи сервер захватывает
`tmp/publish/publish.lock`: системный advisory lock и запись `pid`/`job_id` защищают
от второго процесса. Lock освобождается callback после завершения задачи, файл
остаётся на месте. На Windows проверка PID использует безопасный `OpenProcess`,
а файл сохраняет байт-заполнитель для следующего advisory lock. Запись с
мёртвым PID перезаписывается.

Новый `/start` также отвергается, если есть незакрытая задача с уже отправленными
объявлениями, финансовым шагом от `continue_listing` или `money_click = "clicked"`
(на любом шаге), либо тот же `prep_id` у любой незакрытой задачи. Задачи ищутся
и в памяти, и в checkpoint на диске: второй сервер видит задачи первого, а статус
`closed`/`done` на диске главнее устаревшей записи в памяти. Проверка идёт дважды:
быстро до приёма фото и повторно под lock перед запуском.

`/resume` берёт lock **до** чтения checkpoint и держит его до передачи фоновой
задаче — между решением о продолжении и регистрацией задачи окна нет.

Подготовленные варианты удаляются после `done` лишь когда их не использует другая
незакрытая задача — тоже с учётом дисковых checkpoint.

Повреждённый checkpoint читается как «неизвестный прогресс, клик мог уйти» и
блокирует новый `/start`; закрыть его через `/close` нельзя (409). Выход — проверить
кабинет Авито и вручную убрать каталог задачи из `tmp/publish/` в `trash/`.

## F22: очистка вкладок

Выбран единый владелец Chrome на время публикации: резервирование в процессе и
межпроцессный lock. Существующая очистка вкладок по URL запускается только
внутри владеющей задачи при подключении к Chrome, до создания её собственной
вкладки. Другой пакет в это время не может открыть вкладку публикации через
этот сервис. Логика сценария Авито и финансовых кликов не менялась.

## Контракт API

`GET /api/publish/status/{job_id}` сохраняет прежние поля и добавляет:

- `created_at`: ISO 8601 UTC для новых задач, `null` у старого или неверного значения;
- `is_older_than_24h`: `true`, если прошло не менее 24 часов; при отсутствующем
  или неверном времени тоже `true`.

`POST /api/publish/close/{job_id}` закрывает сохранённую неактивную задачу со
статусом `failed`, `interrupted`, `needs_user_action`, а также `queued`/`running`,
оставшимися после падения процесса (lock при этом свободен). Сначала атомарно записывается checkpoint
со статусом `closed`, затем обновляется память. Чтение и запись происходят под
тем же межпроцессным lock: второй сервер не может закрыть ещё выполняющийся
пакет после локального recovery. Повторное закрытие `closed`
идемпотентно. `closed` не возобновляется и не превращается в `interrupted`
после рестарта.

| Код | Когда |
| --- | --- |
| 200 | Успешный `/start`, `/resume`, `/status` или `/close`; `/close` возвращает `{ "job_id": "…", "status": "closed" }`. |
| 404 | `/close` или `/resume`: нет сохранённой задачи либо неверный `job_id`; `/status`: нет задачи в памяти. |
| 409 | Активный/незакрытый конфликт `/start` и `/resume` (JSON содержит `job_id` блокирующей задачи), живой PID другого процесса, попытка возобновить `closed`, закрыть живую или повреждённую задачу. |
| 422 | `/start`: ошибка полей формы или неподготовленный `prep_id`. |

Статус «отправлено» остаётся отдельным от публикации после модерации.
