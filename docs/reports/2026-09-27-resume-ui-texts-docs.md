## Что изменилось

### Интерфейс

- **F01 (задача теряется при перезагрузке).** `job_id` активной публикации
  теперь сохраняется в `localStorage` (`frontend/src/lib` не трогали —
  функция `rememberJobId` в `DraftPage.jsx`, try/catch на случай
  недоступного хранилища). Опрос статуса (`poll()` в `PublishProgressPanel`)
  больше не останавливается на первой сетевой ошибке: он показывает «нет
  связи с сервером» и повторяет через 3 секунды.
- **Новый маршрут `GET /api/publish/pending`** (`backend/app.py`) — список
  задач, которые не `closed` и не «чистый» `done` (без пропусков); `done` с
  пропусками остаётся в списке (F24/S3 из брифа 05). Собирает задачи и из
  памяти, и с диска, дубли по `job_id` разрешаются в пользу памяти (свежее
  состояние). При открытии экрана формы (`DraftPage`) показывается баннер
  «Есть незавершённая публикация от `<дата>`: отправлено N из M» с кнопками
  «Продолжить»/«Открыть» (если задача ещё выполняется) и «Закрыть задачу».
  Пока баннер есть, кнопка «Опубликовать»/«Подготовить варианты» недоступна —
  **кроме** случая «done с пропусками»: пакет уже отправлен целиком, новая
  публикация дублей не создаст, баннер там только информационный со
  «Скрыть» (без вызова API).
- **F30 (кнопка видна до завершения задачи).** `_publish_resume_view` в
  `app.py` теперь проверяет `ACTIVE_PUBLISH_TASKS[job_id].done()` — пока
  фоновая задача не завершила уборку, `resume_available=false` с текстом
  «Задача ещё завершается — подождите несколько секунд и обновите страницу»
  вместо кнопки, которая тут же получила бы 409.
- **F08 (потолок цены плодит брошенные объявления).** Если
  `user_action.resumable == False` (сейчас — `view_price_cap_exceeded` и
  `view_price_too_low`, `publisher.py`), `resume_available=false` с
  объяснением, что автоматика не предложит «Продолжить со следующего»:
  повтор с тем же потолком может застрять так же на следующем городе.
  Пользователь поднимает потолок и либо завершает объявление вручную, либо
  закрывает задачу.
- **F17 (статус показывает шаг пропущенного объявления).** `/resume` сразу
  выставляет `item_index=start_index`, `step="connect_chrome"` в
  сохраняемом job — до этого несколько секунд показывался номер и шаг ТОЛЬКО
  ЧТО пропущенного объявления.
- **F31 (устаревшая вкладка).** `resumeUnavailableMessage()` во фронте
  раньше игнорировал `resume_unavailable_reason` с бэкенда и показывал один
  и тот же текст про «последнее объявление» независимо от причины — теперь
  берёт причину дословно с сервера (F30/F08/S2 и т.д. теперь видны по
  отдельности, а не одинаковой фразой).
- **F33 (только номер у пропущенного).** Блок пропущенных объявлений
  (`DraftPage.jsx`) показывает номер, город/адрес и ссылку на объявление
  (или id, если ссылки нет) — на любом статусе, включая `done` с пропусками,
  используя поля `skipped_items[].item_id/item_url/city/address` из брифа 05.
- Кнопка «Закрыть задачу» — с `window.confirm`, показывающим число
  отправленных/пропущенных; доступна для `failed`/`needs_user_action`/
  `interrupted` (ровно то, что принимает `POST /api/publish/close`).
  «Продолжить» для задачи старше 24 ч (`is_older_than_24h`) требует
  подтверждения с датой создания и числом отправленных.

## Границы и открытые вопросы

- **«done с пропусками» нельзя закрыть кнопкой.** `POST /api/publish/close`
  (контракт брифа 04) принимает только `queued/running/failed/interrupted/
  needs_user_action/closed` — «завершена с пропусками» (`status=done`) в
  этот список не входит, менять список брифом запрещено (это чужой
  протокол). Баннер и экран публикации это учитывают: кнопки «Закрыть»
  для такой задачи не показывают (иначе она гарантированно ответила бы 409),
  вместо неё — информационный текст и локальное «Скрыть» (только в этой
  вкладке, не вызывает API). Такая задача остаётся в `GET /api/publish/pending`
  и в `tmp/publish/` до ручной уборки — по-прежнему открытый вопрос из
  отчёта брифа 05, решение за владельцем (например, отдельный
  `POST /api/publish/acknowledge/{job_id}` вне рамок этого брифа).
- Логика «безопасно/нет» не продублирована во фронте: `resume_available`,
  `resume_plan`, `resume_unavailable_reason` — целиком с бэкенда; фронт
  только показывает и считает «сколько ещё не начиналось» по уже известному
  полю `step` (F26) — то же самое поле, что фиксирует брифом 05 формат
  `skipped_items[].step`, а не новое решение.

## Ручная проверка баннера (сервер с мёртвым CDP)

**Не выполнялась мной** — при попытке подготовить изолированный запуск
обнаружилось, что `backend/app.py:67` делает `os.chdir(PROJECT_ROOT)`
безусловно при импорте: запуск `python backend/app.py` из отдельного
временного каталога всё равно вернёт процесс в реальный корень проекта, и
`tmp/publish` (путь относительный, `backend/app.py:173`) будет боевым, а не
временным — то есть требование брифа «cwd в отдельном временном каталоге»
само по себе НЕ изолирует `tmp/publish`, несмотря на видимость. Рисковать
боевым checkpoint пользователя ради проверки баннера не стал — по брифу в
этом случае нужна пошаговая инструкция, вот она:

1. Убедитесь, что `frontend/dist/` собран (`cd frontend && npm run build` —
   уже сделано в этой сессии) и что боевой сервер (`localhost:7777`)
   **не запущен** прямо сейчас (иначе следующий шаг будет конфликтовать по
   `tmp/publish/publish.lock`).
2. Посмотрите, есть ли в `tmp/publish/` настоящие подкаталоги с
   `publish-state.json` — если да, не трогайте их, просто временно
   переименуйте `tmp/publish` в `tmp/publish.bak` (PowerShell:
   `Rename-Item tmp\publish tmp\publish.bak`) на время проверки.
3. Создайте пустой `tmp/publish` и положите туда один тестовый job — проще
   всего через Python REPL:
   ```powershell
   $env:AVITO_CDP_URL = "http://127.0.0.1:1"
   .venv\Scripts\python.exe
   ```
   ```python
   import sys; sys.path.insert(0, "backend")
   import publish_state, publisher
   from decimal import Decimal
   from pathlib import Path
   draft = publisher.DraftData(
       title="Тест", trade_type="Продаю своё", condition="Новое с биркой",
       size="", brand="", color="", description="д", price=100,
       locations=(publisher.LocationData("Москва", "улица Тестовая, 1"),
                  publisher.LocationData("Москва", "улица Тестовая, 2")),
       view_price_max=Decimal("2"), photo_paths=(), category="jackets",
   )
   job = {"status": "failed", "step": "fill_title", "items_total": 2,
          "item_index": 1, "items_published": 0, "money_click": "not_clicked"}
   publish_state.save_publish_state(Path("tmp/publish/00000000-0000-0000-0000-000000000001"),
                                     "00000000-0000-0000-0000-000000000001", job, draft)
   exit()
   ```
4. Запустите сервер на отдельном порту с мёртвым CDP (переменная уже
   выставлена в этой же PowerShell-сессии):
   ```powershell
   .venv\Scripts\python.exe -c "import uvicorn, sys; sys.path.insert(0,'backend'); import app; uvicorn.run(app.app, host='127.0.0.1', port=7778)"
   ```
5. Откройте `http://127.0.0.1:7778/draft` — должен появиться баннер «Есть
   незавершённая публикация...», кнопка «Отправить N объявлений на Авито»
   должна быть недоступна.
6. Нажмите «Закрыть задачу», подтвердите — баннер исчезает, кнопка
   отправки становится доступной.
7. Остановите сервер (`Ctrl+C`), удалите тестовый `tmp/publish/00000000-...`,
   верните обратно `tmp/publish.bak` → `tmp/publish`
   (`Remove-Item tmp\publish -Recurse -Force; Rename-Item tmp\publish.bak tmp\publish`).
