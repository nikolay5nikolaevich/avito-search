# iPhone: подготовка объявлений из локальной библиотеки

Статус: одобрена пользователем командой «реализовывай». Дата: 21.10.2026.
Этот документ описывает результат, а не разрешение
на публикацию объявлений или изменение денежного сценария.

## Цель и границы

Для категории iPhone убрать повторный ввод описания и загрузку фотографий.
Пользователь заполняет параметры телефона, цену, потолок просмотра, количество
и геолокации. Сервис находит локальные материалы, готовит обычные черновики
и показывает их для проверки перед отдельным запуском публикации.

Сохраняются текущие уникализация фото, вариации названий, артикулы в описаниях,
редактирование текста черновика, перегенерация, восстановление подготовки,
checkpoint/resume публикации, блокировка параллельных пакетов и денежные проверки.
Другие товарные категории продолжают прежний сценарий ручного ввода.

Не входят в MVP: база адресов, управление файлами через веб-интерфейс,
загрузка своих фото в форме iPhone, смешивание фотопаков в одном запуске,
генерация описаний ИИ, поиск фотографий в интернете, новая уникализация,
автоматическое добавление неподдерживаемых моделей Авито.

## Подтверждённые решения пользователя

- Название вводится на английском; модель определяется независимо от порядка
  слов, например `iPhone 17 Pro Max` и `17 Pro Max iPhone`.
- Память и цвет выбираются отдельными полями. Цвет не ограничивает фотопаки:
  один пак может содержать фотографии телефонов разных цветов.
- Фотопаки разделяются по модели и памяти: коробки на фото могут иметь разную
  маркировку памяти. Pro и Pro Max используют разные библиотеки.
- Один запуск подготовки использует ровно один фотопак. По умолчанию выбор
  случайный; пользователь может выбрать конкретный именованный пак.
- Количество готовых черновиков равно указанному пользователем количеству.
- Описания хранятся отдельно от фото, для каждой модели. Допустимо несколько
  текстов; тексты и условия продажи предоставляет пользователь.
- Всегда: новый, не использовался, неактивированный, коробка запечатана.
- SIM выбирается при каждом заполнении формы: eSIM, SIM + eSIM или SIM + SIM.
- Города и адреса пользователь задаёт текущим способом. База адресов отложена.
- Вид объявления и контактный телефон работают так же, как сейчас.
- Перед публикацией обязательно показываются подготовленные черновики.

## Форма и последовательность действий

При выборе категории iPhone форма содержит:

| Поле | Поведение |
| --- | --- |
| Название | Обязательное; рядом показывается распознанная модель |
| Память | Обязательный выбор из поддерживаемых значений модели |
| Цвет | Обязательный выбор для поля Авито, независимо от фотографий |
| SIM | Обязательный выбор одного из трёх вариантов, без молчаливого значения |
| Цена | Текущая проверка цены товара |
| Потолок просмотра | Текущая проверка максимальной стоимости просмотра |
| Количество | Текущий диапазон 1–20 |
| Фотопак | «Случайный» по умолчанию и имена подходящих паков |
| Геолокации | Текущий список городов/адресов по объявлениям и текущие средства заполнения |
| Вид объявления | Текущий выбор и сохранение значения, без новой константы |

Поля загрузки фотографий и ввода исходного описания в режиме iPhone скрыты.
Постоянные характеристики показаны короткой справочной строкой; заполнять их
не требуется. Контактный телефон не получает нового правила или новой формы.

1. Название определяет модель; память определяет доступные фотопаки.
2. Пользователь видит наличие материалов и выбирает случайный/конкретный пак.
3. «Подготовить» фиксирует параметры и материалы, создаёт N черновиков.
4. В результате видны выбранный пак, фотографии и итоговые тексты. Ручная правка
   текста и перегенерация карточки сохраняются.
5. Публикация запускается только отдельным действием из существующего сценария.

Смена модели/памяти сбрасывает несовместимый выбор пака. Несовместимые память
и цвет очищаются при смене модели. Смена исходных характеристик/пака после
подготовки требует новой подготовки: старый текст нельзя отправить с новыми
структурированными характеристиками. Старые publish-задачи возобновляются
из собственного checkpoint, без чтения текущей формы.

## Библиотека на диске

Предлагаемое техническое решение для одобрения: папка `library/iphone/`
в корне проекта, без отдельной СУБД и без установок дополнительных сервисов.
Фото и пользовательские описания локальные, не включаются в git. При реализации
добавить исключение и инструкцию, как открыть папку и наполнить библиотеку.

```text
library/iphone/
  iPhone 17 Pro Max/
    descriptions/
      01.txt
      02.txt
    512 GB/
      Пак 1/
        01.jpg
        02.jpg
      Пак 2/
        01.jpg
        02.jpg
    1024 GB/
      Пак 1/
        01.jpg
        02.jpg
  iPhone 17 Pro/
    descriptions/
      01.txt
    1024 GB/
      Пак 1/
        01.jpg
```

Правила папок фиксированы и описаны в инструкции: каноническое имя модели,
объём в GB (`1024 GB` для 1 ТБ), произвольное имя пака. Это не язык свободных
правил и не распознавание содержимого фотографии. Имена `01`, `02` задают
порядок фотографий; первая становится основной. Используются текущие лимиты,
форматы и проверки загрузки фото. Посторонние файлы вроде `Thumbs.db` игнорируются.
Пустой, повреждённый или превышающий лимиты пак недоступен с понятной причиной;
лишние фотографии не отбрасываются молча.

Каталог перечитывается при запросе доступных материалов и перед подготовкой;
в интерфейсе есть обновление списка без перезапуска сервера. Исчезнувший выбранный
пак вызывает ошибку, а не молчаливую замену. Случайный выбор равновероятен среди
пригодных паков модели/памяти; повтор пака в разных запусках допустим.
Отсутствие подходящих паков или текстов блокирует подготовку с указанием
ожидаемой папки. Материалы другой модели/памяти не используются как запасные.

Сервер принимает идентификатор пака, а не произвольный путь клиента. Разрешённые
пути проверяются внутри корня библиотеки, включая разрешение ссылок/junction.
Внешние пути и обход через `..` недопустимы.

## Распознавание модели

Использовать конечный словарь моделей и допустимых английских сочетаний.
Регистр и повторные пробелы несущественны; порядок `iPhone` относительно модели
может меняться. `Pro Max` распознаётся целиком до проверки `Pro`.
Нельзя распознать неизвестную модель как похожую известную: `iPhone 18`
не означает `iPhone 18 Pro`, `17e` не означает `17`.

Поддержка ограничена подтверждёнными моделями/памятью/цветами в профиле проекта.
Обычный iPhone 18 сейчас отсутствует в нём: показать неподдерживаемую модель,
не выбирать другую. Новые модели требуют отдельной проверки формы Авито.
Если в названии несколько моделей или распознавание неоднозначно — исправление
названия до подготовки. Явные противоречия памяти в названии и отдельном поле
также требуют исправления; алгоритм не переписывает название молча.

## Описания и подстановки

UTF-8 `.txt` хранит авторский текст с сохранением абзацев и пробелов.
Поддерживаемые необязательные подстановки:

| Маркер | Значение |
| --- | --- |
| `{модель}` | Каноническая модель, например iPhone 17 Pro Max |
| `{память}` | Выбранная память в принятом в форме представлении |
| `{цвет}` | Один выбранный цвет поля Авито |
| `{SIM}` | Выбранный вариант SIM |

Список нескольких доступных цветов пользователь пишет обычным текстом;
он не заменяется одним выбранным цветом. Автоматического списка цветов нет.
Комплект, подарки, гарантия и условия не придумываются и не дописываются.
Неизвестный маркер формата `{...}` — понятная ошибка шаблона.

Предлагаемое решение: для каждого черновика случайно выбрать один из текстов
модели, независимо от других черновиков; повторы допустимы. Подставить значения,
затем применить существующее добавление уникального артикула. Вариации заголовка
и обработка фото остаются существующими. Никакой перефразировки шаблона.

Структурированные характеристики — источник значений для формы Авито; выбор SIM
больше не выводится только из текста описания. Отсутствие слов о SIM/активации
в шаблоне допустимо, если характеристики заданы формой/постоянными настройками.
Явное противоречие текста этим данным должно блокировать публикацию до денежных
действий с понятным сообщением. Существующие проверки противоречивых утверждений
об активации/упаковке сохраняются; не обещается понимание произвольного текста.
Проверка выполняется и после ручной правки описания.

## Фиксация материалов и восстановление

Перед генерацией выбранные фото копируются в папку подготовки, тексты и параметры
сохраняются вместе с ней. Сохраняются модель, память, цвет, SIM, выбранный пак,
выбор текста для каждой карточки и данные случайной генерации. Изменение библиотеки
после подготовки не меняет уже показанные черновики или будущий resume.

Восстановление после перезапуска детерминированно использует этот снимок.
Перегенерация одной карточки меняет существующую уникализацию/артикул/название,
но сохраняет фотопак и выбранный для карточки исходный шаблон. Другие карточки
не меняются. Для смены пака нужна новая подготовка, не новый запуск публикации
уже частично опубликованного пакета.

Старые подготовки/checkpoint без новых полей читаются совместимо. Неизвестный
SIM старой задачи нельзя автоматически считать SIM + eSIM: сохраняется прежний
проверенный путь либо понятная остановка до действий, требующих этих данных.

## Технические точки и предварительная проверка Авито

Текущие точки входа: `frontend/src/pages/DraftPage.jsx`, `frontend/src/lib/publish.js`,
`backend/app.py`, `backend/preparation.py`, `backend/text_variation.py`,
`backend/category_profiles.py`, `backend/publisher.py`, `backend/publish_state.py`.
Конкретное разделение файлов и API выбирает исполнитель в плане реализации.
Использовать текущий конвейер подготовки и публикации, не строить второй.

Сейчас `_phone_required_options` подтверждает по описанию только SIM + eSIM.
Поддержка трёх вариантов требует отдельного структурированного поля SIM во всём
пути: форма → запрос → подготовка → публикация → checkpoint → resume.
Показ выбранного SIM в превью обязателен.

До реализации живого выбора eSIM и SIM + SIM проверить существующие локальные
снимки/тесты формы; если данных нет, подготовить пользователю безопасную команду
разведки без публикации. Порог проверки: для каждого варианта подтверждены
точная подпись, идентификатор и способ обратного чтения выбранного значения.
Неизвестные ID не угадываются. Если порог не достигнут — участок живого выбора
получает BLOCKED с доказательствами и следующим действием; нельзя объявлять
полную поддержку трёх вариантов по одним локальным тестам.

Денежный сценарий не меняется: минимальная доступная ставка допустима только
в пределах потолка; неопределённость останавливает процесс; финансовые клики
не ретраятся. Все ограничения AGENTS.md сохраняются.

## Приёмка

Независимый от реализации агент заранее пишет acceptance-тесты от этих исходов:

1. Английские варианты порядка слов определяют одну модель; Pro/Pro Max,
   17/17e и неизвестные модели не смешиваются.
2. Память отбирает правильную папку; цвет не влияет на подбор фотопака.
3. В режиме случайного выбора все N карточек используют один зафиксированный
   пак; ручной выбор точно используется, включая порядок и главное фото.
4. Для каждой из N карточек работает прежняя уникализация фото, названия
   различаются, описания получают уникальные артикулы. Исходные файлы неизменны.
5. Подстановки модели/памяти/цвета/SIM корректны; статический список цветов,
   телефон, пробелы и абзацы сохранены, включая CRLF в Windows.
6. Пустая библиотека, неверные шаблоны, повреждённые/слишком большие паки,
   исчезнувшие файлы и выход пути за корень дают понятный отказ подготовки.
7. Правка текста остаётся доступна. Противоречие постоянным характеристикам
   или выбранному SIM не проходит в публикацию.
8. Перегенерация одной карточки сохраняет её пак/шаблон, остальные не меняются.
   Перезапуск и изменение библиотеки не меняют сохранённые материалы подготовки.
9. Все три SIM проходят сохранение/восстановление, а живые селекторы проверены
   по фактам. Старые подготовки и resume не получают выдуманных значений.
10. UI iPhone не требует фото/описания; остальные категории, геолокации,
    вид объявления, контактный телефон и денежные проверки работают как прежде.
11. После подготовки нет автоматической публикации. Смена параметров не позволяет
    опубликовать устаревшее превью под новыми характеристиками.

Проверки не требуют платной публикации. В отчёте реализации перечислить файлы,
команды и точные результаты, отдельно границы проверки живой формы Авито.

## Что ещё потребуется от пользователя

До реального использования нужны фотографии и окончательные тексты описаний.
Их отсутствие не мешает реализации и тестам на синтетических материалах.
Документ и предложенные технические решения одобрены. План реализации:
`docs/_internal/iphone-library/plan.md`. Коммит — только по отдельной просьбе.
