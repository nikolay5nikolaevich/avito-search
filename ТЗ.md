## 0. Статус разведки и артефакты

Разведка живой формы `avito.ru/additem` (категория «Пиджаки и костюмы») выполнена
2026-06-09 по HTML, снятому пользователем из залогиненного Chrome:

- `debug/additem.html` — полный отрендеренный DOM формы (содержит персональные данные
  пользователя — телефон, email, координаты; `debug/` в `.gitignore`, НЕ коммитить);
- `debug/additem_map.txt` — выжимка: все `data-marker`, все опции селектов с ID;
- `debug/extract_additem_map.py` — скрипт извлечения карты из дампа (переиспользовать,
  когда Авито поменяет вёрстку: положить новый дамп в `debug/additem.html` и перезапустить).

Все селекторы и ID в этом ТЗ взяты из этих артефактов — это подтверждённые данные,
не предположения.

## 1. Цель

Добавить в текущий локальный сервис второй сценарий: подготовку и сохранение
**черновика** объявления Avito из интерфейса проекта. Работает в том же проекте, что и
аналитика спроса, через уже открытый пользователем Chrome (`start-chrome.bat` + CDP).

## 2. ЖЁСТКИЕ ПРАВИЛА БЕЗОПАСНОСТИ (читать первыми)

1. **НИКОГДА не кликать кнопку «Продолжить»** (`[data-marker='item-edit/button-next']`).
   Она ведёт к публикации. У аккаунта пользователя подключён платный тариф с оплатой
   просмотров — случайная публикация = списание реальных денег. Единственная разрешённая
   финальная кнопка — **«Сохранить и выйти»** (`[data-marker='item-creator/save-and-exit']`).
   В коде `publisher.py` селектор `button-next` может встречаться только в комментарии-предупреждении.
2. Не хранить логин/пароль/куки аккаунта. Авторизация — только живой Chrome пользователя.
3. Не закрывать браузер пользователя целиком; закрывать только свои вкладки.
4. Поля «Телефон», «Способ связи», «Предложение» (`params[196527]`), «Целевая аудитория»
   (`params[181941]`), блок тарифа — предзаполнены аккаунтом, **не трогать вообще**.
5. Ошибка любого шага не должна ронять backend и не должна приводить к клику по
   незапланированным кнопкам. Сомневаешься, что на экране, — стоп, дамп, статус
   `needs_user_action`.

## 3. Границы первой версии

Покрывает: одна категория `Товары → Личные вещи → Одежда, обувь, аксессуары →
Мужская одежда → Пиджаки и костюмы`; результат — черновик в аккаунте; источник данных —
форма проекта; 1 запуск = 1 черновик.

НЕ покрывает: автопубликацию, продвижение, хранение учётных данных, работу без
`start-chrome.bat`, другие категории, генерацию адресов, обход капчи/антибота/модерации,
видоизменение фото и текста, пакетный режим. Пакетный режим — только отдельным следующим
этапом после проверки базового сценария.

## 4. Пользовательский сценарий

1. Пользователь запускает `start-chrome.bat`, в Chrome руками заходит на avito.ru,
   проверяет, что залогинен.
2. Запускает проект (`python backend/app.py`), открывает `localhost:8000`.
3. На фронте открывает экран «Черновик объявления» (отдельная страница рядом с аналитикой).
4. Заполняет форму, загружает фото, жмёт кнопку запуска.
5. Видит экран прогресса с человекочитаемыми шагами.
6. По завершении — итоговый статус; черновик виден в аккаунте Avito
   (Мои объявления → Черновики).

## 6. Вход на форму и АВТОМАТИЧЕСКИЙ выбор категории (РАЗВЕДАНО ЖИВЬЁМ 2026-06-10)

**Факт.** `goto /additem` открывает НЕ форму, а экран **«Новое объявление»** с выбором
категории (подтвердил Codex 2026-06-09 + живой скрин). Прежний дамп `additem.html` был снят
с уже открытого черновика — нетипичный старт. Поэтому выбор категории — обязательный
автоматический шаг `select_category`.

**Разведка выполнена (CDP, 2026-06-10):** через уже открытый Chrome пользователя сняты
`debug/newitem.html`, `debug/newitem_markers.txt`, `debug/current_clickables.txt`,
`debug/refine_report.txt`; алгоритм проверен сквозняком `debug/recon_full.py` —
доходит до hidden `27/748/754` и костюмной формы. Селекторы НЕ угаданы, а подтверждены.

### 6.1 Подтверждённое устройство экрана (миллер-мастер, НЕ поиск)
- Поля поиска категории НЕТ. Это дерево-колонки. Каждый пункт любого уровня —
  `button[data-marker='category-wizard/button']` с названием категории внутри (текст может
  содержать `&nbsp;` → нормализовать пробелы при сравнении). «Другая категория» —
  отдельный маркер `another-category` (не нужен).
- Полноэкранный picker (`Новое объявление`) — кнопки мастера есть, хлебных крошек
  `[data-marker='category-title']` НЕТ.
- На форме крошки `category-title` — это `<a role="button">`, КЛИК по ним раскрывает
  миллер-мастер поверх формы.
- Колонки появляются ПРОГРЕССИВНО: клик по пункту добавляет следующую колонку. Повторный
  клик по уже выбранному пункту его СХЛОПЫВАЕТ (важно для алгоритма).
- Кнопка «Сохранить и выйти» (`item-creator/save-and-exit`) появляется ТОЛЬКО когда в форме
  есть данные; на пустой форме внизу «Выйти» (`item-creator/exit`). «Продолжить»/«Разместить»
  (`item-edit/button-next`) — публикация, НЕ кликать (§2).

### 6.2 Алгоритм `select_category` (реализован, проверен live)
1. `goto /additem`, ждать до 30 с состояния: `form` (есть крошки) | `picker` (есть кнопки
   мастера, крошек нет) | `unknown` (капча/иное → дамп, `needs_user_action`).
2. Если категория уже целевая (hidden 27/748/754) → пропустить (черновик переоткрыт).
3. Если `picker` → клик по верхнему разделу «Личные вещи» → дождаться крошек (форма).
4. Клик по крошкам `category-title` → раскрыть миллер-мастер.
5. Досверлить полный путь `Личные вещи → Одежда, обувь, аксессуары → Мужская одежда →
   Пиджаки и костюмы` кликами по `category-wizard/button` (сравнение по нормализованному
   тексту, кликать только видимые). **Правило:** НЕ кликать уровень, чей подуровень уже
   виден (иначе схлопнется); последний пункт кликать всегда.
6. Дождаться hidden 27/748/754; иначе дамп + `needs_user_action`.

Реализация: `publisher._step_open_form` / `_step_select_category` / `_drill_category_path`,
селекторы `avito_publish_selectors.CATEGORY_WIZARD_BUTTON` и `CATEGORY_FULL_PATH`.

### 6.3 Поведение в пакетном режиме (§16)
Шаг `select_category` выполняется для КАЖДОГО черновика (повторное /additem снова показывает
выбор). Часть `open_form`-фазы каждой итерации.

### 6.4 Что осталось проверить живьём (за пользователем)
Read-only разведка дошла до целевой формы, но ПОЛНЫЙ прогон публикатора (фото → гео →
«Сохранить и выйти» → черновик в аккаунте) пользователь запускает вручную (автозапуск против
живого аккаунта запрещён политикой). Хрупкие места при ручной проверке: гео-саджест и
появление кнопки «Сохранить и выйти».

## 7. Форма на frontend

Отдельная страница (React Router, рядом с Workspace), явная пометка: «Работает только
категория "Пиджаки и костюмы" (мужская одежда)».

Поля (все обязательные, кроме помеченных):

- Название — текст;
- Вид объявления — select из 3 значений (дефолт «Продаю своё»);
- Состояние — radio из 4 значений;
- Фотографии — multiple file input, 1–10 файлов, jpeg/png/gif/heic; превью списка
  выбранных файлов (имя + размер) до запуска;
- Размер — select из 24 значений Авито;
- Бренд — текст;
- Цвет — select из 17 значений Авито;
- Описание — textarea;
- Цена — число > 0, целое, в рублях;
- Город — select (можно переиспользовать справочник `cities.py`, но допустим и простой
  текст — город нужен только как префикс строки адреса);
- Адрес — текст (улица, дом). На Авито уходит склейка «{Город}, {Адрес}».

После запуска — переход на экран прогресса (или ссылка на него).

## 8. Валидация

Frontend и backend валидируют независимо; backend не доверяет фронту:

- название непустое; описание непустое; бренд непустой;
- цена задана, целое число > 0;
- файлов фото 1–10; mime/расширение из списка accept; разумный лимит размера
  (например ≤ 25 МБ/файл);
- город выбран, адрес непустой;
- вид объявления / состояние / размер / цвет — значение из соответствующего словаря
  (валидировать по ключам словарей из `avito_publish_selectors.py`).

Ошибки валидации возвращать как HTTP 422 с перечнем полей — это ошибки запроса,
НЕ ошибки задачи (задача не создаётся).

ВНИМАНИЕ: добавлен шаг `select_category` (см. §6 — подтверждено живой проверкой, что
/additem открывает экран выбора категории, а не форму). Нумерация шагов сдвинулась.

   (§6.1: поиск категории → клик подсказки, резерв — дерево категорий). Если форма уже
   готова с верной категорией — шаг проходится мгновенно (no-op). Неудача выбора → дамп,
   `needs_user_action`.
4. `check_category` — контроль 27/748/754 или крошки «Пиджаки и костюмы» (§6); не совпало
   → `needs_user_action` с дампом.
5. `fill_title` — название.
6. `upload_photos` — `set_input_files` на `add/input`; ждать появления превью загруженных
   фото / исчезновения индикатора загрузки (таймаут с запасом: фото грузятся на сервер).
7. `fill_fields` — вид объявления, состояние, размер, бренд, цвет (комбобоксы: клик по
   `*/select-text` → клик по `*/option(ID)`; радио — клик по label).
8. `fill_description` — contenteditable (§5); проверить `description_html` непустой.
9. `fill_price` — цена.
10. `fill_address` — гео-саджест (§5); если саджест не появился или hidden `address`
    остался пуст → `needs_user_action` с дампом.
11. `save_draft` — клик «Сохранить и выйти»; успех = навигация со страницы формы
    (смена URL) без модалки ошибки. Зафиксировать конечный URL в результате.
12. `done`.

Шаг `select_category` имеет человекочитаемую подпись «Выбор категории». Существующий код
publisher.py (шаги без select_category) нужно ОБНОВИТЬ под новую последовательность:
вставить шаг между open_form и check_category, поправить STEPS/STEP_LABELS/TOTAL_STEPS и
все тесты, завязанные на номера/количество шагов (smoke и фронтовый PUBLISH_STEPS).

Между шагами — паузы 0.5–1.5 с (человекоподобность, у Авито антибот). После каждого
изменения поля полезно убеждаться, что значение применилось (Авито на React — иногда
нужен `dispatchEvent`/клавиатурный ввод вместо прямого `.fill()`; если `.fill()` не
сработал — fallback на `page.keyboard.type`).

Статусы задачи: `queued`, `running`, `needs_user_action`, `done`, `failed`.
`needs_user_action` в v1 — **терминальный** (без resume): задача останавливается,
пользователь получает понятную инструкцию что сделать руками и перезапускает заново.
Триггеры: капча, неожиданный экран, не та категория, мёртвый гео-саджест.

Хранение задач: отдельный dict `PUBLISH_JOBS` в `app.py` (не смешивать с `JOBS`
аналитики). Кэша для publish-задач НЕТ (в отличие от аналитики).

Файлы: фото из multipart сохранять в `tmp/publish/{job_id}/` (создать, добавить `tmp/`
в `.gitignore`). После `done` — удалять директорию; при `failed`/`needs_user_action` —
оставлять для разбора. Диагностика при любом фейле шага: скриншот + HTML в
`debug/publish/{job_id}/step_{имя}.png|.html`.

Логи: отдельный логгер `publisher` (файл `logs/publisher.log`), ключевые шаги и ошибки.
Изменения вёрстки Авито (не найден селектор) логировать с пометкой `SELECTOR_MISS`.

## 10. API

## 14. Известные риски (учесть в реализации)

- **Гео-саджест** — самое хрупкое место: ввод должен быть «живым» (посимвольно с
  задержкой), саджест может не появиться без фокуса. Предусмотреть 2–3 ретрая ввода.
- **Описание** — contenteditable, `.fill()` не подойдёт; контроль через hidden
  `description_html`.
- **`title-field-23`** — суффикс может оказаться динамическим; использовать
  `input[name='title']`.
- **Комбобоксы Авито** (РАЗВЕДАНО 2026-06-10, `debug/recon_combobox_open.py`): кастомный
  `<div role="combobox">`. Внутри СКРЫТЫ и `*/select-text` (span), и нативный `*/select`
  → кликать их или `select_option` НЕЛЬЗЯ (невидимы, actionability падает). Алгоритм:
  (1) клик по КОНТЕЙНЕРУ `[data-marker='{prefix}']` — раскрыть; (2) клик по ВИДИМОМУ `<div>`
  с текстом опции (пункты списка БЕЗ data-marker, маркеры option(ID) на скрытых `<option>`);
  (3) верификация — нативный `*/select` получил value == ID опции; фолбэк — ввод лейбла в
  `*/search-input`. Реализовано в `publisher._select_combobox`.
- **Черновик уже существует** — Авито может открыть форму с прошлыми данными. В v1:
  перед заполнением очищать перезаписываемые поля (у названия есть `*/clear`; текстовые
  поля — Ctrl+A → ввод). Поля, которые мы не заполняем, не трогать.
- Вёрстка Авито меняется: при `SELECTOR_MISS` — дамп и понятная ошибка, новый дамп
  прогонять через `debug/extract_additem_map.py`.

## 16. Пакетный режим (v1.1, добавлено 2026-06-09)

Из одной формы создаётся **N одинаковых черновиков** (N выбирает пользователь, 1–10,
дефолт 1, поле «Сколько черновиков» на форме). Без вариативности текста/фото (обход
антиспама остаётся вне рамок — пользователь правит черновики руками перед публикацией).

Реализация:
- `POST /api/publish/start` — новое поле `drafts_count` (int 1–10, валидация на обеих сторонах);
- черновики делаются **последовательно** в одной задаче: полный цикл шагов 2–11 (§9,
  включая `select_category` — §6.2) на каждый, пауза 5–15 с между черновиками;
- статус: добавить `draft_index` (текущий, с 1), `drafts_total`, `drafts_saved`;
  `step/step_label/done/total` остаются про текущий черновик. Фронт показывает
  «Черновик i из N» + шаги текущего;
- результат: `drafts_saved` и список конечных URL по сохранённым черновикам;
- **защита от перезаписи:** перед `fill_title` черновика i>1 проверить, что поле названия
  пустое; если там название предыдущего черновика — Авито переоткрыл тот же черновик →
  стоп, `needs_user_action` («Авито переоткрывает существующий черновик; сохранено i-1 из N»),
  дамп в debug/publish/{job_id}/;
- падение/капча на черновике k — задача останавливается, `drafts_saved = k-1`, частичный
  успех честно отражается в статусе и результате;
- открытие формы для каждого следующего черновика — заново `goto /additem` (§6 целиком,
  включая контроль категории).

## 17. Вариативность черновиков против антиспама (v3, переработано 2026-06-10)

> v3 (брейншторм с пользователем 2026-06-10): текст — ТОЛЬКО локальный комбинаторный
> движок (Claude API и `llm.py` ИСКЛЮЧЕНЫ решением пользователя — ключа нет и не будет);
> зеркало исключено из фото-пула; добавлена лёгкая вариация НАЗВАНИЯ; вариант №1 — всегда
> оригинал. Пошаговый план реализации — **`ТЗ-вариативность-план.md`**.

Развитие §16. Сейчас пакет = N **одинаковых** черновиков → Авито может склеить их как
дубли. Цель: из ОДНОГО введённого объявления (название + описание + фото) сервис делает N
**различающихся** вариантов (по одному на черновик), чтобы снизить риск блокировки за
дубликаты. Пользователь правит/публикует черновики дальше сам.

### 17.1 Принятые решения (закрытые развилки; подтверждены пользователем 2026-06-10)
- **Фото — только локально (Pillow), без нейросети.** Товар реальный: AI-перерисовка
  исказила бы внешний вид и обманула покупателя/модерацию. Меняем перцептивный хэш, не суть.
- **Текст — ТОЛЬКО локальный комбинаторный движок, БЕЗ Claude API.** Решение пользователя:
  API-ключа нет и заводить не планирует. `llm.py` НЕ создаётся, зависимость `anthropic`
  НЕ добавляется, VPN-развязка для фазы подготовки не нужна (всё локально и без сети).
- **Две фазы с превью.** Сначала «Подготовить варианты» (генерация + показ), отдельно
  «Запустить черновики». Пользователь видит тексты/фото ДО заливки и может перегенерировать
  неудачные варианты — для локального перефраза это особенно важно.
- **«Одна технология на черновик»:** все фото ОДНОГО черновика обработаны ОДНИМ пресетом
  (единый стиль внутри объявления); между черновиками пресеты/параметры разные.
- **Название тоже варьируется (лёгкая вариация).** Одинаковые заголовки — самый заметный
  признак дубля; все варианты названия видны в превью до заливки.
- **Вариант №1 — всегда нетронутый оригинал** (название и описание как ввёл пользователь;
  фото — нейтральный пресет: только чистка EXIF + лёгкое пережатие). Предсказуемость:
  первый черновик = ровно то, что ввели.
- **Зеркало по горизонтали ИСКЛЮЧЕНО из фото-пула** (в v2 было): борт мужского пиджака
  застёгивается на определённую сторону, бирки/логотипы на фото зеркалятся — покупатель
  и модерация заметят подделку.

### 17.2 Честные оговорки (не переобещать)
- Антиспам Авито — чёрный ящик; вариативность СНИЖАЕТ риск склейки, но НЕ гарантирует
  отсутствие блокировки. Нигде в UI/доках не обещать «не забанит».
- Локальный перефраз слабее ИИ: тексты остаются «родственными» (общая лексика и структура).
  Это осознанный трейд-оф за бесплатность/оффлайн; в UI не приукрашивать.
- Факты сохраняются «по построению»: движок НЕ выдумывает новые слова — только переставляет
  предложения, заменяет по словарю синонимов и добавляет нейтральные шаблонные фразы.

### 17.3 Новые модули backend
- `backend/text_variation.py` — БЕЗ сети:
  `vary_listing(title: str, description: str, n: int, *, seed: int | None = None,
  facts: dict | None = None) -> list[TextVariant]`, где TextVariant = (title, description,
  notes), `facts` — опциональные размер/состояние/бренд из формы для добавок в название.
  Четыре независимые «ручки» описания, комбинируемые от seed:
  1) перестановка предложений (первое — смысловое ядро — фиксировано);
  2) словарь синонимов лексики объявлений (~50–100 пар, модульная константа:
     «отличное состояние»→«прекрасное/идеальное состояние», «продаю»→«продам», …);
  3) пул шапок/подвалов (~10+10 нейтральных шаблонов: «Отвечу на вопросы в сообщениях»,
     «Самовывоз или отправка» и т.п.);
  4) оформление: маркеры «—»/«•», переносы строк, порядок блоков.
  Название: перестановка слов + добавки из `facts` («Пиджак Hugo Boss 48 M» /
  «Hugo Boss пиджак, 48 (M), отличное состояние»).
  Вариант 1 = оригинал (untouched). Контроль непохожести: Jaccard по 3-граммам слов
  для всех пар описаний ≤ порога (например 0.85); похожие пересобирать с другими
  параметрами (ограничить число попыток, затем форс-добавить другую шапку/подвал).
  Один и тот же seed → воспроизводимый результат; перегенерация = новый seed.
  Самотесты в `__main__`.
- `backend/photo_variation.py`:
  - `build_presets(n: int, seed=None) -> list[Preset]` — N пресетов из пула «семейств»:
    лёгкий зум-кроп 2–6% (к центру или со смещением); микро-поворот ±1..2° с обрезкой
    полей; яркость/контраст/насыщенность ±3–8%; лёгкий сдвиг цветовой температуры;
    слабый гауссов шум; пере-сжатие JPEG с качеством 85–95. ЗЕРКАЛА НЕТ (§17.1).
    Пресет №1 — нейтральный (только EXIF + пережатие). Каждый Preset — связная комбинация
    2–3 семейств с конкретными параметрами; во ВСЕХ всегда чистка EXIF. При N больше
    размера пула — переиспользуем семейства с другими параметрами, пресеты попарно различны.
  - `apply_preset(image_bytes: bytes, preset: Preset) -> bytes` — Pillow-трансформации;
    результат — валидный JPEG/PNG разумного размера. Ошибка на конкретном фото → лог +
    вернуть оригинал этого фото (не валить черновик), пометить в результате.
  - Параметры держать «мягкими» (не уродовать фото). Самотесты в `__main__`: пресеты
    различны; apply не падает на маленьких/нечётных/CMYK картинках; размеры адекватны.
- `backend/preparation.py` — оркестратор фазы 1: фоновая задача подготовки (по образцу
  `run_job`/`run_publish_job`): вызывает `text_variation` и `photo_variation`, раскладывает
  результаты в хранилище (§17.4), ведёт статус в `PREP_JOBS`. Сетевых вызовов НЕТ.

### 17.4 Хранилище
`tmp/publish/prep_{prep_id}/draft_{NN}/`:
- `photos/` — обработанные фото варианта (имена сохраняют порядок исходных);
- `title.txt` — название варианта;
- `text.txt` — описание варианта;
- `meta.json` — имя пресета фото, seed, заметки об ошибках.
Очистка: после успешной фазы 2 удалять весь `prep_{prep_id}`; при падении — оставлять.
`tmp/` уже в `.gitignore`.

### 17.5 API (тумблера use_api НЕТ — текст всегда локальный)
- `POST /api/publish/prepare` — `multipart/form-data`: название, базовое описание, базовые
  фото (1–10), `drafts_count` (1–10), опционально размер/состояние/бренд (для добавок в
  название). Валидация (как §8 для текста/фото/числа) → 422. Создаёт ФОНОВУЮ задачу
  подготовки (до 10 черновиков × до 10 фото — секунды на Pillow). Возвращает `{prep_id}`.
  Хранилище задач — отдельный dict `PREP_JOBS`.
- `GET /api/publish/prepare/status/{prep_id}` → `{prep_id, status, step_label, done, total, error}`
  (статусы queued/running/done/failed; шаги: «Генерация текстов», «Обработка фото»).
- `GET /api/publish/prepare/result/{prep_id}` → `{prep_id, drafts: [{index, title,
  description, preset_name, photo_urls: [...], notes}]}` для превью.
- `GET /api/publish/prepare/photo/{prep_id}/{draft_index}/{photo_index}` → отдаёт
  обработанную картинку для превью (image/jpeg|png).
- `POST /api/publish/prepare/regenerate` — `{prep_id, draft_index}`: перегенерирует ОДИН
  черновик целиком (текст + фото) с новым seed. Вариант №1 не перегенерируется (оригинал).
- `POST /api/publish/start` — расширяется: принимает `prep_id`. Если он задан — публикатор
  берёт для черновика i название/описание/фото из `prep_{prep_id}/draft_{i}/`. Если
  `prep_id` НЕ задан — поведение §16 (одинаковые), полная обратная совместимость.

### 17.6 Изменения в publisher.py
- `run_publish_job`: если в задаче есть `prep_id`, на каждой итерации i загружать
  `title.txt`, `text.txt` и `photos/*` варианта i (вместо базовых) и подавать их в
  `fill_title`, `fill_description` и `upload_photos`. Защита от перезаписи (§16) сравнивает
  с названием ВАРИАНТА i (с разными заголовками становится только надёжнее). Остальные
  шаги и предохранители (§2) — без изменений. Если папки варианта i нет/пуста → шаг падает
  с понятной ошибкой, дамп.

### 17.7 Frontend
Поток страницы «Черновик»: форма (как сейчас) → кнопка **«Подготовить варианты»** → экран
**превью**: на каждый из N черновиков карточка (номер, название, текст описания, ряд
миниатюр обработанных фото, имя фото-пресета, заметки), кнопка **«Перегенерировать»**
(на карточке; для №1 недоступна — это оригинал) и общая **«Запустить N черновиков»** →
существующий экран прогресса (§16). Тексты по-русски, стиль — как в текущем DraftPage.
Превью-картинки грузить с `/api/publish/prepare/photo/...`. Тумблера use_api нет.

### 17.8 Обработка ошибок
- Ошибка трансформации одного фото → оригинал этого фото + заметка в meta/notes.
- Ошибки валидации (название/текст пусты, фото 0 или >10, drafts_count вне 1–10) → 422,
  задача не создаётся.
- Любая ошибка фазы — лог в `logs/publisher.log`, статус failed, без падения backend.

### 17.9 Тестирование
