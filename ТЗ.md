# ТЗ: модуль подготовки черновиков Avito

## 1. Цель

Добавить в текущий локальный сервис второй сценарий работы: подготовку и сохранение
черновика объявления Avito из интерфейса проекта.

Новый сценарий должен работать в том же проекте, что и текущая аналитика спроса, и
использовать уже открытый пользователем Chrome, запущенный через `start-chrome.bat`.

## 2. Контекст проекта

Сейчас проект умеет:

- запускать локальный backend на FastAPI;
- показывать frontend на React/Vite;
- работать с Avito через Playwright;
- подключаться к уже открытому пользовательскому Chrome по CDP.

Текущая основа уже есть в:

- `backend/app.py` — оркестрация задач и API;
- `backend/parser.py` — Playwright/CDP-логика;
- `frontend/src/pages/WorkspacePage.jsx` — основной рабочий экран.

Новый модуль должен переиспользовать этот подход, а не создавать отдельный сервис.

## 3. Границы первой версии

Первая версия покрывает только один сценарий:

- категория: `Товары -> Личные вещи -> Одежда, обувь, аксессуары -> Мужская одежда -> Пиджаки и костюмы`;
- результат: `черновик сохранен в аккаунте Avito`;
- источник авторизации: только уже открытый и залогиненный Chrome пользователя;
- источник данных объявления: форма внутри текущего проекта.

Первая версия не покрывает:

- автопубликацию;
- продвижение и платные услуги;
- хранение логина/пароля от аккаунта;
- фоновую авторизацию без пользователя;
- работу без `start-chrome.bat`;
- многокатегорийность;
- генерацию случайных адресов;
- обход антиспама, антибота и модерации;
- автоматическое видоизменение фото и текста для снижения детекта;
- массовый пакетный режим из одного шаблона в несколько разных объявлений.

Примечание: пакетный режим и вариативные объявления могут обсуждаться только как
отдельный следующий этап, после проверки базового сценария `1 форма -> 1 черновик`.

## 4. Пользовательский сценарий

1. Пользователь запускает `start-chrome.bat`.
2. В открывшемся Chrome пользователь вручную открывает Avito и убеждается, что аккаунт
   уже залогинен.
3. Пользователь запускает проект.
4. На frontend появляется отдельный экран `Подготовка черновика`.
5. Пользователь заполняет форму объявления.
6. Пользователь загружает реальные фото товара через форму сервиса.
7. Пользователь выбирает город и указывает один реальный адрес.
8. Пользователь нажимает кнопку запуска.
9. Backend создает задачу, подключается к открытому Chrome, открывает форму создания
   объявления на Avito, проходит нужную категорию, заполняет поля и сохраняет черновик.
10. Пользователь видит прогресс, текущий шаг и итоговый статус.
11. После завершения черновик должен появиться в аккаунте Avito.

## 5. Форма на frontend

Нужен отдельный экран рядом с аналитикой спроса.

Форма первой версии должна содержать:

- `Название объявления`
- `Вид объявления`
- `Состояние`
- `Фотографии`
- `Размер`
- `Бренд`
- `Цвет`
- `Описание объявления`
- `Цена`
- `Город`
- `Адрес`

Дополнительные требования к форме:

- обязательные поля валидируются до отправки;
- загрузка фото поддерживает несколько файлов;
- пользователь видит список выбранных фото до запуска;
- форма должна явно показывать, что работает только категория `Пиджаки и костюмы`;
- у пользователя должна быть понятная кнопка запуска задачи;
- после запуска форма должна показывать ссылку или переход на экран прогресса.

## 6. Валидация данных

Frontend и backend независимо валидируют входные данные.

Минимальные требования:

- название не пустое;
- описание не пустое;
- цена задана и больше нуля;
- выбран хотя бы один файл фото;
- выбран город;
- адрес не пустой;
- значения характеристик не пустые;
- количество фото не превышает лимит Avito, если лимит известен и стабилен.

Backend не должен доверять только frontend-валидации.

## 7. Логика backend

Для сценария подготовки черновиков нужен отдельный модуль, например
`backend/publisher.py`.

Задачи модуля:

- принять нормализованные данные формы;
- сохранить загруженные фото во временную директорию задачи;
- подключиться к пользовательскому Chrome по CDP;
- открыть создание объявления на Avito;
- выбрать нужную категорию;
- заполнить поля;
- загрузить фото;
- сохранить объявление как черновик;
- вернуть итог задачи и диагностическую информацию.

Логика должна быть отделена от текущего парсера спроса, но может переиспользовать
вспомогательные функции подключения к CDP и общие настройки Playwright.

## 8. Изменения в структуре проекта

Планируемые изменения по файлам:

- `backend/app.py`
  - добавить новые маршруты API для сценария черновиков;
  - добавить отдельное хранилище статусов задач или изолировать новый тип задач в
    текущем механизме.
- `backend/publisher.py`
  - новый модуль сценария подготовки черновика;
  - шаги Playwright для формы Avito;
  - обработка статусов и ошибок.
- `backend/avito_publish_selectors.py`
  - отдельный файл селекторов формы публикации Avito;
  - не смешивать селекторы публикации с селекторами аналитики.
- `frontend/src/pages/`
  - добавить отдельную страницу или режим для подготовки черновика.
- `frontend/src/lib/api.js`
  - добавить методы работы с новым API.
- `tests/`
  - добавить smoke-тест веб-слоя с подменой publisher-логики.

## 9. API

Предлагаемые маршруты:

- `POST /api/publish/start`
  - принимает форму и файлы;
  - создает фоновую задачу;
  - возвращает `job_id`.
- `GET /api/publish/status/{job_id}`
  - возвращает состояние задачи;
  - используется для polling.
- `GET /api/publish/result/{job_id}`
  - возвращает итог задачи, ошибки и служебные данные.

Минимальный формат статуса:

- `job_id`
- `status`
- `step`
- `done`
- `total`
- `error`

Для первой версии `total` и `done` могут быть завязаны на шаги сценария, а не на
пакет объявлений.

## 10. Состояния задачи

Нужны как минимум следующие статусы:

- `queued`
- `running`
- `needs_user_action`
- `done`
- `failed`

`needs_user_action` нужен для ситуаций, когда Avito требует ручное вмешательство:

- капча;
- подтверждение;
- неожиданный экран;
- нестандартное состояние формы.

После такого статуса пользователь должен понимать, что делать дальше.

## 11. Экран прогресса

Экран прогресса должен показывать:

- текущий этап;
- финальный или промежуточный статус;
- текст ошибки, если она есть;
- краткую сводку по введенным данным;
- факт успешного сохранения черновика.

Желательно показывать этапы в человекочитаемом виде, например:

- `Подключение к Chrome`
- `Открытие формы Avito`
- `Выбор категории`
- `Загрузка фотографий`
- `Заполнение характеристик`
- `Сохранение черновика`

## 12. Работа с Playwright и Chrome

Ключевые требования:

- использовать только уже открытый Chrome пользователя через CDP;
- не закрывать пользовательский браузер целиком;
- закрывать только свои вкладки и свои временные ресурсы;
- не ломать текущий сценарий аналитики спроса.

Если подключение к `CDP_URL` недоступно, задача должна завершаться понятной ошибкой
с подсказкой: сначала запустить `start-chrome.bat`.

## 13. Логи и временные файлы

Нужны:

- отдельный логгер сценария публикации;
- записи ключевых шагов;
- запись текстов ошибок;
- при необходимости диагностические скриншоты и HTML проблемного шага.

Временные файлы:

- загруженные фото сохраняются во временную директорию задачи;
- после завершения задачи временные файлы очищаются;
- при падении может сохраняться отладочный набор, если это помогает разбору.

## 14. Надежность и обработка ошибок

Требования:

- ошибка не должна ронять весь backend;
- пользователь всегда должен получать финальный статус;
- ошибки валидации должны отделяться от ошибок Playwright/CDP;
- нужно различать ошибки формы Avito и ошибки локального сервиса;
- неожиданные изменения верстки Avito должны логироваться отдельно.

## 15. Тестирование

Для первой версии нужны:

- smoke-тест API-слоя без реального выхода на Avito;
- тесты валидации входных данных;
- ручная проверка на одном черновике через реальный Chrome.

Минимальный ручной сценарий проверки:

1. Запустить `start-chrome.bat`.
2. Залогиниться в Avito.
3. Открыть экран подготовки черновика.
4. Заполнить форму.
5. Загрузить фото.
6. Запустить задачу.
7. Убедиться, что черновик появился в аккаунте.

## 16. Критерии приемки

Функция считается готовой для первой версии, если:

- в проекте есть отдельный экран подготовки черновика;
- сценарий работает через `start-chrome.bat`;
- приложение не хранит учетные данные пользователя;
- пользователь может заполнить форму и запустить задачу;
- сервис сохраняет черновик в аккаунт Avito;
- пользователь видит прогресс и итог;
- при ошибке сервер не падает;
- текущая аналитика спроса продолжает работать без регрессии.

## 17. Что важно не забыть при реализации

- селекторы формы Avito надо держать отдельно от селекторов аналитики;
- сценарий публикации и сценарий парсинга не должны мешать друг другу;
- после правок логики черновиков нужен отдельный smoke-тест;
- при живой проверке особенно важно проверить поведение загрузки фото и сохранения
  черновика на реальной форме Avito;
- в первой версии не расширять сценарий сверх одной категории и одного черновика за запуск.
